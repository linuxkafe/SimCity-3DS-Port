## Attribution attempt — `svc=0x32`

27 commits in the Oct-10 → Oct-18 window. `frontend/3ds/3dsdbg.c` (19) and
`3ds_main.c` (14) dominate. The **network/FTP bridge is new in this window**:
`9268482` "Host an FTP server inside the running app", plus the socket-lifecycle
commits `7213151`, `336ae09`, `d3390e5`, `8e8b8b9`, `eb7c29a`, `bbc3825`.

**Error-family link (strongest signal so far).** `3dsdbg.c:950` already documents
a known socInit failure observed as **`0xD8E073EC`**. The recurring fault is
**`raw=0xD8E007F7`** — same `0xD8E0` prefix, different suffix. Both sit in the
`soc:u` service error range rather than in ordinary game code. That is
circumstantial, not proof: it links the fault to the network stack that this
window introduced, and to nothing else currently suspect.

**Cadence does not implicate a sleep.** There is no `usleep`/`sleep`/`svcSleepThread`
in the frontend. A regular ~3.1 s repeat therefore comes from *something* on a
timer — the emulator's own socket handling, or one call per slow frame. Frames
here are seconds apart, so "once per frame" and "once per 3 s" are not yet
distinguishable. **Do not treat the cadence as evidence of a retry loop.**

**What this rules out:** the boot path. Boot is proven good on both binaries, and
`dbgk_init()` runs once, so a *repeating* fault does not come from it.

## The decisive experiment (not yet run)

One variable, two arms, same protocol as above:

1. Add a compile-time switch that skips `dbgk_init()`'s `socInit`/socket/bind and
   the FTP listener.
2. Arm A — network bridge on (current build, already measured: stalls at frame 5,
   85 faults).
3. Arm B — bridge compiled out. If the stall **and** the `svc=0x32` faults both
   disappear, the network stack is implicated. If only the faults disappear and the
   stall remains, they are two problems. If neither changes, the network stack is
   exonerated and the window's other changes need bisecting.

There is currently **no such switch** — `DBGK_HOST_TEST` skips socInit but is the
host-test path, not a device-side disable. Build is Docker-only here
(`make docker-build`, `-DPLATFORM=3DS`); `arm-none-eabi-gcc` is absent on this host.

## RESULT — the network bridge is exonerated

Switch added: `DS3_NET_BRIDGE` (default 1) in `frontend/3ds/3ds_main.c`, guarding
`dbgk_init()`, `ds3ftp_init/poll/exit()`, wired through `CMakeLists.txt`.
**Arms built from the identical tree** so the switch is the only variable — the
first attempt at this was confounded (Deck binary was Oct-18, arm B was HEAD) and
was thrown away rather than reported.

|---|---|---|---|---|---|
| A′ | 1 | `6dec648ac5b37d237ec789289a2dbbd3` | dies after `boot:` | **0** | `ConfigureNew3DSCPU` |
| B | 0 | `682ac59b9b87bc31011709f3417c1fbe` | dies after `boot:` | **0** | `ConfigureNew3DSCPU` |

### ❌ CORRECTION — the control DOES reproduce. The failure below was my harness.

Everything in the table above is wrong. The control is stable and reproduces its
result every run. Two bugs in the ad-hoc measurement, both mine:

1. **`timeout N` did not bound the run.** `run.sh` `exec`s the AppImage, which
   does not die on SIGTERM, so `timeout 45 ./run.sh` returned only when the *ssh

   the remote command line *contains* that literal, so the kill hit the measuring
   shell and aborted the remaining steps. Every "0 advances" reading was taken
   with the run never having finished. Fixed by assembling the pattern remotely

## Interpretation (kept separate on purpose)

The blocker is a **hang, not a fault exit**. The 0.2%→0.0% CPU and sleeping
threads mean no 3DS thread is executing. The SVC 0x32 cadence is regular enough
(~3.1 s) to look like a timer rather than a crash path, but that is a guess and
nothing here establishes what it is.

## NOT ESTABLISHED

- Whether `svc=0x32` **causes** the wedge or merely accompanies it. It is new
  (0 → 85) and it is in the stalling build, but co-occurrence across two builds
  is not causation. The discriminator is a run with the call stubbed or the fault
  counted per-frame against advance progress.
- What the `svc=0x32` call is. No disassembly of the built binary yet.
- Why the Oct-10 build needed `ConfigureNew3DSCPU` and the current one does not —
  i.e. which source change fixed it. That fix is the most valuable recent work and
  is currently undocumented.
- Whether input is required to advance. `auto-advance` is on, and the Oct-18-10:27
  log shows `input=0008` by frame 300 — no run has shown whether input *causes*
  motion or merely accompanies it.
- Whether the real 3DS behaves the same. **Everything here is emulated.** The
  physical device at `10.0.0.130` was unreachable — ARP FAILED, no such host on
  this LAN — so no hardware comparison was possible this session.
- Whether the `anon_pipe_write` block is a cause or a consequence of the hang.
- Frame rate. `cclog` was off in both runs today (it costs ~14.5×); the Oct-18
  10:27 log that reached frame 300 had it on, so that run's pacing is not
  comparable to either run above.
